CampusShield AI — Kiro Specification
1. Project Goal
Convert the existing CampusShield AI project into a cloud-ready, multi-tenant SaaS product for AI-powered network traffic analysis and cyber-threat detection.
The existing project must be preserved and improved. Do not replace working functionality unnecessarily.
AWS target region: us-east-1
The implementation must solve the currently known issues:
1. Alerts generated by simulations appear in notifications but do not appear in Incident Feed / Alert Management.
2. Sessions created by simulations/analysis do not appear as completed sessions in Executive Reports.

6. Analysis Session Requirements
Every analysis or simulation must create a persistent analysis session.
Session lifecycle:
RUNNING
   |
   +----> COMPLETED
   |
   +----> FAILED
A session must not exist only in memory.
When analysis starts:
- Create session record.
- Set status to RUNNING.
- Store start timestamp.
When processing finishes successfully:
- Store analysis result.
- Set status to COMPLETED.
- Store completion timestamp.
When processing fails:
- Set status to FAILED.
- Store useful error/status information.
This is required to fix the Executive Reports problem.
7. Alert Requirements
When threat detection identifies suspicious activity:
1. Create an alert.
2. Persist the alert in DynamoDB.
3. Associate it with the correct tenant.
4. Associate it with the analysis session.
5. Store severity and threat information.
6. Return the result to the frontend.
Example alert fields:
alertId
tenantId
sessionId
severity
threatType
score
target
message
status
createdAt
The persisted alert must be the single source of truth.
The notification panel and Incident Feed must use the same persisted alert data.
Do NOT maintain separate unrelated in-memory alert lists for different pages.

13. Security Requirements
- Use Cognito authentication.
- Validate authorization on every protected API.
- Enforce tenant isolation.
- Use least-privilege IAM roles.
- Do not store secrets in source code.
- Use environment variables or AWS configuration/secrets mechanisms.
- Use HTTPS through CloudFront/API Gateway.
- Validate URL, file and request inputs.
- Enforce upload/file size limits.
- Log useful errors without exposing sensitive information.

16. Acceptance Criteria
The implementation is successful when:
1. A new user can sign up/sign in.
2. The user reaches the SaaS dashboard after authentication.
3. A supported simulation produces a result.
4. A supported analysis produces a result.
5. Every analysis creates a persistent session.
6. A successful analysis marks the session COMPLETED.
7. A failed analysis marks the session FAILED.
8. Detected threats create persistent alerts.
9. The same persisted alert appears in Notifications and Incident Feed.
10. Incident Feed no longer incorrectly shows "No Alerts" when alerts exist.
11. Executive Reports lists completed sessions.
12. A completed session can generate a PDF report.
13. The generated report is stored in S3.
14. Report metadata is stored in DynamoDB.
15. Tenant A cannot access Tenant B's data.
16. The application can be deployed to AWS in us-east-1.

- Inspect current frontend.
- Inspect current backend.
- Inspect current APIs.
- Inspect current database/session/alert logic.
- Identify reusable components.
- Do not rewrite working code unnecessarily.
Phase 2 — Persistent Data Model
- Implement/adapt DynamoDB entities.
- Create session persistence.
- Create alert persistence.
- Create report metadata persistence.
Phase 3 — Backend
- Implement/adapt API Gateway/Lambda APIs.
- Integrate Cognito authentication.
- Enforce tenant authorization.
- Integrate existing detection/ML logic.
Phase 4 — Fix Alerts
- Persist generated alerts.
- Connect Incident Feed to persisted alerts.

18. Important Kiro Instruction
Do not blindly rewrite the entire project.
First inspect the existing codebase and identify:
- Existing routes
- Existing API contracts
- Existing database models
- Existing detection logic
- Existing authentication
- Existing frontend pages
- Existing simulation logic
Then modify the project incrementally to satisfy this specification.
Preserve working features unless they conflict with the target SaaS architecture.
Before major changes, explain what will be changed and why.
After each major phase:
1. Build the project.
2. Run tests/health checks.
3. Verify the affected feature.
4. Fix errors before continuing.
Do not hard-code secrets, API keys, AWS access keys, or passwords.
